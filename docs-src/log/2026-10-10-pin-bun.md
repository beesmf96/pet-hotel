# Bun pinned to one version for CI and Docker

## Asked
"Can we upgrade our bun setup?", then "yes, pin it". The host had Bun
1.3.13, the Docker `node` image (`oven/bun:alpine`) was a cached 1.3.14, and
CI took `latest` (1.4.2). `bun audit` on 1.3 had no `fix` command and could
in principle disagree with CI's audit.

## Done
- Local: the host Bun went to 1.4.2 with `bun upgrade`. Nothing in the repo
  records the host version; `.bun-version` is the one to match.
- Repo: `.bun-version` holds `1.4.2`. All three `setup-bun` steps in
  `ci.yml` read it with `bun-version-file` instead of `bun-version: latest`.
- Docker: the `node` service uses `oven/bun:1.4.2-alpine`. Compose cannot
  read a version file, so the tag is a hand-kept copy.
- Test: `tests/Unit/BunVersionTest.php` checks the file holds an exact
  version, the compose tag matches it, and every CI Bun setup reads the file.
  To upgrade Bun, change `.bun-version` and the compose tag together.

## Not done
- No `packageManager` field in `package.json`. Bun does not enforce it, so it
  would be a third copy with nothing checking it.
- The host is not checked. A developer on an older Bun still works; only the
  lockfile format or audit results could differ.

## Produced
- ADR: none
- Knowledge: none
- Intake: none — Bun and the `oven/bun` image were already in use; only the
  version is now fixed.

## Verified
- New `BunVersionTest`: 3 passed. Setting `.bun-version` to 1.4.3 makes the
  compose check fail, as intended.
- `composer test` in the app container: 396 passed, 1359 assertions.
  `vendor/bin/pint --test`: 164 files pass. No JS changed.
- `docker compose exec node bun --version` prints 1.4.2 on the pinned image.
